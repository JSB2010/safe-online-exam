# Portable School Deployment Guide

This guide deploys one school-specific instance of the Canvas Safe Exam Browser LTI app. The supported portable model is:

- One Cloud Run service per school/environment.
- One configured Canvas base URL per Cloud Run service.
- One Firestore database per Cloud Run service.
- School-specific URLs, client IDs, private keys, and certificates stored in Secret Manager.

This is intentionally not a shared multi-school runtime. If one Cloud Run service later needs to host multiple Canvas instances, the data model must become tenant-scoped first.

## Prerequisites

You need:

- A Google Cloud project with billing enabled. Use separate projects for production and non-production when possible.
- `gcloud` authenticated to that project.
- A Canvas root-account admin.
- A Canvas API OAuth developer key for REST API access.
- An LTI 1.3 developer key for the tool launch.
- A Safe Exam Browser config-encryption certificate identity for student devices.

This guide assumes `gcloud` is already installed and authenticated. It includes the steps to create or retrieve every app secret that has to land in Google Secret Manager.

## Credential Inventory

Create one row of values for each school/environment. Do not reuse values between unrelated schools or between prod and non-prod unless you intentionally want those environments linked.

| App value                        | Secret name with `SECRET_PREFIX=school_canvas_seb` | Where it comes from                                                                                                                                                                                         |
| -------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CANVAS_DOMAIN`                  | `school_canvas_seb_canvas_domain`                  | The school's Canvas base URL, for example `https://school.instructure.com` or the school's Canvas vanity domain. Use the production Canvas host unless this Cloud Run service is for Canvas beta/test only. |
| `TOOL_URL`                       | `school_canvas_seb_tool_url`                       | The Cloud Run service URL returned by `gcloud run services describe`, or the custom HTTPS domain mapped to the service.                                                                                     |
| `LTI_CLIENT_ID`                  | `school_canvas_seb_lti_client_id`                  | Canvas LTI 1.3 Developer Key `Client ID`, copied after creating and enabling the LTI key.                                                                                                                   |
| `LTI_PRIVATE_KEY`                | `school_canvas_seb_lti_private_key`                | Generated by this repo with `npm run generate:lti-key`; store the private JWK JSON in Secret Manager. Canvas receives the matching public key from `${TOOL_URL}/.well-known/jwks.json`.                     |
| `LTI_DEPLOYMENT_ID`              | `school_canvas_seb_lti_deployment_id`              | Canvas External App `Deployment ID`, visible after installing the LTI app by Client ID. Cloud Run requires it and rejects launches from other deployments of the same LTI key.                              |
| `CANVAS_API_CLIENT_ID`           | `school_canvas_seb_api_client_id`                  | Canvas API OAuth Developer Key ID/client ID. This is separate from the LTI client ID.                                                                                                                       |
| `CANVAS_API_CLIENT_SECRET`       | `school_canvas_seb_api_client_secret`              | Canvas API OAuth Developer Key secret/key. Treat it like a password.                                                                                                                                        |
| `CANVAS_REDIRECT_URI`            | usually not a secret                               | Defaults to `${TOOL_URL}/api/oauth2callback`. Configure the same URI on the Canvas API OAuth Developer Key.                                                                                                 |
| `SESSION_SECRET`                 | `school_canvas_seb_session_secret`                 | Generated locally with `openssl rand -base64 48`.                                                                                                                                                           |
| `STATE_ENCRYPTION_KEY`           | `school_canvas_seb_state_encryption_key`           | Generated locally with `openssl rand -base64 48`.                                                                                                                                                           |
| `SEB_CONFIG_ENCRYPTION_CERT_PEM` | `school_canvas_seb_seb_config_encryption_cert_pem` | Public certificate PEM generated by `scripts/generate-seb-config-cert.sh`. Do not store the private `.p12` in Cloud Run.                                                                                    |
| `GCP_PROJECT_ID`                 | plain Cloud Run env var                            | Google Cloud project ID.                                                                                                                                                                                    |
| `FIRESTORE_DATABASE_ID`          | plain Cloud Run env var                            | Firestore database ID created for this school/environment.                                                                                                                                                  |

The Canvas API OAuth credentials and the Canvas LTI credentials are intentionally separate. The OAuth key lets instructors authorize REST API calls for quiz discovery and access-code writes. The LTI key lets Canvas launch the tool.

## Bootstrap Order

There is one unavoidable ordering issue: Canvas requires final HTTPS URLs before you can create correct Developer Keys, but a generated Cloud Run URL is not known until the service exists.

Use one of these paths:

- If the school will use a custom domain, map that domain and use it as `TOOL_URL` before creating Canvas keys.
- If the school will use the generated `run.app` URL, create placeholder Canvas secrets, deploy once, retrieve the real Cloud Run URL, create the Canvas keys, update the secrets, and redeploy.

The placeholder bootstrap deploy is only to discover the Cloud Run URL. Do not install the Canvas app or run exams until the real Canvas key values have been written to Secret Manager and the service has been redeployed.

Set common shell variables:

```bash
export PROJECT_ID="your-gcp-project-id"
export REGION="us-central1"
export SERVICE_NAME="school-canvas-seb"
export REPOSITORY="canvas-seb-repo"
export IMAGE_NAME="school-canvas-seb"
export FIRESTORE_DATABASE_ID="school-canvas-seb"
export SECRET_PREFIX="school_canvas_seb"
export SERVICE_ACCOUNT="seb-canvas-school-prod"
export CANVAS_DOMAIN="https://school.instructure.com"
export TOOL_URL="https://placeholder.invalid"
export LTI_CLIENT_ID="bootstrap-pending"
export LTI_DEPLOYMENT_ID="bootstrap-pending"
export CANVAS_API_CLIENT_ID="bootstrap-pending"
export CANVAS_API_CLIENT_SECRET="bootstrap-pending"
```

Replace the Canvas values after the first deploy, or set them to real values now if you already have a final custom `TOOL_URL`.

## Enable GCP APIs

```bash
gcloud config set project "${PROJECT_ID}"

gcloud services enable \
  artifactregistry.googleapis.com \
  cloudbuild.googleapis.com \
  run.googleapis.com \
  firestore.googleapis.com \
  secretmanager.googleapis.com \
  iam.googleapis.com
```

## Create Artifact Registry

```bash
gcloud artifacts repositories create "${REPOSITORY}" \
  --repository-format=docker \
  --location="${REGION}" \
  --description="Canvas SEB LTI images"
```

If the repository already exists, keep it and continue.

## Create Runtime Service Account

```bash
gcloud iam service-accounts create "${SERVICE_ACCOUNT}" \
  --display-name="Canvas SEB Cloud Run runtime"
```

Grant Firestore access only to this deployment's database. The IAM condition prevents the runtime identity from using the same role against another database in the project:

```bash
gcloud projects add-iam-policy-binding "${PROJECT_ID}" \
  --member="serviceAccount:${SERVICE_ACCOUNT}@${PROJECT_ID}.iam.gserviceaccount.com" \
  --role="roles/datastore.user" \
  --condition="expression=resource.name == 'projects/${PROJECT_ID}/databases/${FIRESTORE_DATABASE_ID}',title=canvas_seb_database,description=Limit Canvas SEB runtime to its Firestore database"
```

Do not grant the runtime service account project-wide Secret Manager access. Exact secret-resource bindings are added after the required secrets exist. The Cloud Run runtime identity also does not need Artifact Registry Reader; Cloud Build performs the image pull/deploy operation.

Grant Cloud Build permission to deploy and use the runtime service account:

```bash
PROJECT_NUMBER="$(gcloud projects describe "${PROJECT_ID}" --format='value(projectNumber)')"
CLOUDBUILD_SA="${PROJECT_NUMBER}@cloudbuild.gserviceaccount.com"

gcloud projects add-iam-policy-binding "${PROJECT_ID}" \
  --member="serviceAccount:${CLOUDBUILD_SA}" \
  --role="roles/run.admin"

gcloud projects add-iam-policy-binding "${PROJECT_ID}" \
  --member="serviceAccount:${CLOUDBUILD_SA}" \
  --role="roles/artifactregistry.writer"

gcloud iam service-accounts add-iam-policy-binding "${SERVICE_ACCOUNT}@${PROJECT_ID}.iam.gserviceaccount.com" \
  --member="serviceAccount:${CLOUDBUILD_SA}" \
  --role="roles/iam.serviceAccountUser"
```

## Create Firestore Database

Create a Firestore Native database with the selected ID:

```bash
gcloud firestore databases create \
  --database="${FIRESTORE_DATABASE_ID}" \
  --location="${REGION}" \
  --edition=standard \
  --type=firestore-native
```

Create TTL policies on the `expiresAt` field for these collections:

- `sessions`
- `transientStates`
- `operationLocks`

Firestore TTL can be configured from the Google Cloud console. Use the configured database, collection group name, and field `expiresAt`.

## Generate Runtime Secrets

Generate random secrets:

```bash
openssl rand -base64 48 > /tmp/session-secret.txt
openssl rand -base64 48 > /tmp/state-encryption-key.txt
```

Generate an LTI private JWK:

```bash
npm ci
npm run generate:lti-key -- "${SERVICE_NAME}" > /tmp/lti-private-key.jwk.json
```

Generate an SEB config-encryption certificate. The password is read from a mode-0600 file, never an environment variable or process argument:

```bash
umask 077
mkdir -p .local
openssl rand -base64 48 > .local/seb-cert-p12-password
SEB_CERT_NAME="${SERVICE_NAME}-seb-config-encryption" \
SEB_CERT_SUBJECT="/CN=SEB Canvas LTI Config Encryption/O=School Name" \
bash scripts/generate-seb-config-cert.sh \
  .local/seb-certs \
  .local/seb-cert-p12-password
```

Vault the generated `.p12`, private PEM, and password file using the certificate runbook, then remove workstation copies. Only the public certificate PEM belongs in the Cloud Run runtime. Deploy the private identity to managed clients with an MDM Certificates payload configured as non-extractable and restricted to SEB; do not use script or policy parameters to carry it.

Managed Macs need macOS 12.1 or newer and a school-approved SEB build (3.6.x stable or newer): generated assessment configs enforce Apple's Automatic Assessment Configuration (AAC) assessment mode and refuse to run on older macOS releases. AAC needs no MDM supervision or special entitlement — SEB ships with the assessment entitlement — but the MDM baseline for the installed SEB client should mirror the AAC preference (Preferences → Security → prefer/enforce Assessment Mode) so a locally started SEB session cannot run with a weaker kiosk mode than the exam configs demand. Note that AAC blocks third-party assistive technology; plan separate proctoring accommodations for students who rely on such tools instead of weakening the baseline.

## Create Secret Manager Entries

Create the required secrets. If you are using the bootstrap path, the Canvas values can still be `bootstrap-pending`; replace them after the first deploy and Canvas setup.

The provided Cloud Build configs mount `:latest` Secret Manager versions. After adding a new secret version, redeploy Cloud Run so the new revision receives that version. If a school's policy requires pinned secret versions, replace `:latest` in the Cloud Build config with explicit numeric versions and update those numbers during rotations.

```bash
printf '%s' "${CANVAS_DOMAIN}" | gcloud secrets create "${SECRET_PREFIX}_canvas_domain" --replication-policy=automatic --data-file=-
printf '%s' "${TOOL_URL}" | gcloud secrets create "${SECRET_PREFIX}_tool_url" --replication-policy=automatic --data-file=-
printf '%s' "${LTI_CLIENT_ID}" | gcloud secrets create "${SECRET_PREFIX}_lti_client_id" --replication-policy=automatic --data-file=-
printf '%s' "${LTI_DEPLOYMENT_ID}" | gcloud secrets create "${SECRET_PREFIX}_lti_deployment_id" --replication-policy=automatic --data-file=-
gcloud secrets create "${SECRET_PREFIX}_lti_private_key" --replication-policy=automatic --data-file=/tmp/lti-private-key.jwk.json
gcloud secrets create "${SECRET_PREFIX}_session_secret" --replication-policy=automatic --data-file=/tmp/session-secret.txt
gcloud secrets create "${SECRET_PREFIX}_state_encryption_key" --replication-policy=automatic --data-file=/tmp/state-encryption-key.txt
printf '%s' "${CANVAS_API_CLIENT_ID}" | gcloud secrets create "${SECRET_PREFIX}_api_client_id" --replication-policy=automatic --data-file=-
printf '%s' "${CANVAS_API_CLIENT_SECRET}" | gcloud secrets create "${SECRET_PREFIX}_api_client_secret" --replication-policy=automatic --data-file=-
gcloud secrets create "${SECRET_PREFIX}_seb_config_encryption_cert_pem" \
  --replication-policy=automatic \
  --data-file=".local/seb-certs/${SERVICE_NAME}-seb-config-encryption.crt.pem"
```

Grant the runtime identity access to exactly those ten secrets, not every secret in the project:

```bash
for SECRET_NAME in \
  "${SECRET_PREFIX}_canvas_domain" \
  "${SECRET_PREFIX}_tool_url" \
  "${SECRET_PREFIX}_lti_client_id" \
  "${SECRET_PREFIX}_lti_deployment_id" \
  "${SECRET_PREFIX}_lti_private_key" \
  "${SECRET_PREFIX}_session_secret" \
  "${SECRET_PREFIX}_state_encryption_key" \
  "${SECRET_PREFIX}_api_client_id" \
  "${SECRET_PREFIX}_api_client_secret" \
  "${SECRET_PREFIX}_seb_config_encryption_cert_pem"
do
  gcloud secrets add-iam-policy-binding "${SECRET_NAME}" \
    --member="serviceAccount:${SERVICE_ACCOUNT}@${PROJECT_ID}.iam.gserviceaccount.com" \
    --role="roles/secretmanager.secretAccessor"
done
```

If a secret already exists, add a new version instead:

```bash
printf '%s' "${TOOL_URL}" | gcloud secrets versions add "${SECRET_PREFIX}_tool_url" --data-file=-
```

Delete temporary secret files after Secret Manager versions are created:

```bash
rm -f /tmp/session-secret.txt /tmp/state-encryption-key.txt /tmp/lti-private-key.jwk.json
```

## First Deploy

Run the portable Cloud Build:

```bash
gcloud builds submit \
  --config=cloudbuild-school.yaml \
  --substitutions=_LOCATION="${REGION}",_REPOSITORY="${REPOSITORY}",_SERVICE="${SERVICE_NAME}",_IMAGE="${IMAGE_NAME}",_FIRESTORE_DATABASE_ID="${FIRESTORE_DATABASE_ID}",_SECRET_PREFIX="${SECRET_PREFIX}",_SERVICE_ACCOUNT="${SERVICE_ACCOUNT}"
```

After the first deploy, get the Cloud Run URL:

```bash
gcloud run services describe "${SERVICE_NAME}" \
  --region="${REGION}" \
  --format='value(status.url)'
```

Store the final URL:

```bash
export TOOL_URL="$(gcloud run services describe "${SERVICE_NAME}" --region="${REGION}" --format='value(status.url)')"
printf '%s' "${TOOL_URL}" | gcloud secrets versions add "${SECRET_PREFIX}_tool_url" --data-file=-
```

## Retrieve Canvas Credentials

Use [canvas-school-setup.md](canvas-school-setup.md) for the detailed Canvas UI path. The values to record are:

1. `CANVAS_DOMAIN`: the Canvas base URL, with no trailing slash and no path. Example: `https://school.instructure.com`.
2. `CANVAS_API_CLIENT_ID`: the Canvas API OAuth Developer Key ID/client ID.
3. `CANVAS_API_CLIENT_SECRET`: the Canvas API OAuth Developer Key secret/key.
4. `LTI_CLIENT_ID`: the Canvas LTI 1.3 Developer Key Client ID.
5. `LTI_DEPLOYMENT_ID`: the External App deployment ID shown after installing the app by Client ID.

The Canvas API OAuth developer key must use this redirect URI:

```text
${TOOL_URL}/api/oauth2callback
```

If scoped API developer keys are enabled, grant these exact scopes:

```text
url:GET|/api/v1/courses/:course_id/quizzes
url:GET|/api/v1/courses/:course_id/assignments
url:GET|/api/quiz/v1/courses/:course_id/quizzes/:assignment_id
url:PUT|/api/v1/courses/:course_id/quizzes/:id
url:PATCH|/api/quiz/v1/courses/:course_id/quizzes/:assignment_id
```

The Canvas LTI 1.3 developer key should be configured from:

```text
${TOOL_URL}/lti/config
```

That JSON config points Canvas at:

- OIDC initiation URL: `${TOOL_URL}/lti/login`
- Target link URI: `${TOOL_URL}/lti/launch`
- Redirect URI: `${TOOL_URL}/lti/launch`
- Public JWK URL: `${TOOL_URL}/.well-known/jwks.json`

After recording the real Canvas values, update the existing Secret Manager secrets:

```bash
export LTI_CLIENT_ID="REPLACE_WITH_CANVAS_LTI_CLIENT_ID"
export LTI_DEPLOYMENT_ID="REPLACE_WITH_CANVAS_DEPLOYMENT_ID"
export CANVAS_API_CLIENT_ID="REPLACE_WITH_CANVAS_API_CLIENT_ID"
export CANVAS_API_CLIENT_SECRET="REPLACE_WITH_CANVAS_API_CLIENT_SECRET"

printf '%s' "${CANVAS_DOMAIN}" | gcloud secrets versions add "${SECRET_PREFIX}_canvas_domain" --data-file=-
printf '%s' "${TOOL_URL}" | gcloud secrets versions add "${SECRET_PREFIX}_tool_url" --data-file=-
printf '%s' "${LTI_CLIENT_ID}" | gcloud secrets versions add "${SECRET_PREFIX}_lti_client_id" --data-file=-
printf '%s' "${LTI_DEPLOYMENT_ID}" | gcloud secrets versions add "${SECRET_PREFIX}_lti_deployment_id" --data-file=-
printf '%s' "${CANVAS_API_CLIENT_ID}" | gcloud secrets versions add "${SECRET_PREFIX}_api_client_id" --data-file=-
printf '%s' "${CANVAS_API_CLIENT_SECRET}" | gcloud secrets versions add "${SECRET_PREFIX}_api_client_secret" --data-file=-
```

Do not leave the bootstrap deployment ID in place. `cloudbuild-school.yaml` always mounts the deployment-ID secret, and the service rejects any signed launch whose deployment claim does not match it.

## Redeploy With Real Secrets

Redeploy after updating Secret Manager so Cloud Run receives a new revision with the current `latest` secret versions:

```bash
gcloud builds submit \
  --config=cloudbuild-school.yaml \
  --substitutions=_LOCATION="${REGION}",_REPOSITORY="${REPOSITORY}",_SERVICE="${SERVICE_NAME}",_IMAGE="${IMAGE_NAME}",_FIRESTORE_DATABASE_ID="${FIRESTORE_DATABASE_ID}",_SECRET_PREFIX="${SECRET_PREFIX}",_SERVICE_ACCOUNT="${SERVICE_ACCOUNT}"
```

Then confirm Cloud Run still reports the same `TOOL_URL`:

```bash
gcloud run services describe "${SERVICE_NAME}" \
  --region="${REGION}" \
  --format='value(status.url)'
```

## Canvas Configuration

After the redeploy, install and verify Canvas using these deployed URLs:

```text
JSON configuration URL: ${TOOL_URL}/lti/config
OIDC initiation URL:    ${TOOL_URL}/lti/login
Target link URI:        ${TOOL_URL}/lti/launch
Redirect URI:           ${TOOL_URL}/lti/launch
Public JWK URL:         ${TOOL_URL}/.well-known/jwks.json
OAuth redirect URI:     ${TOOL_URL}/api/oauth2callback
Detector script URL:    ${TOOL_URL}/js/canvas-seb-detector.js
```

See [canvas-school-setup.md](canvas-school-setup.md) for the Canvas UI steps.

If only the `TOOL_URL` changed and all Canvas keys already exist, update just that secret and redeploy:

```bash
printf '%s' "${TOOL_URL}" | gcloud secrets versions add "${SECRET_PREFIX}_tool_url" --data-file=-

gcloud builds submit \
  --config=cloudbuild-school.yaml \
  --substitutions=_LOCATION="${REGION}",_REPOSITORY="${REPOSITORY}",_SERVICE="${SERVICE_NAME}",_IMAGE="${IMAGE_NAME}",_FIRESTORE_DATABASE_ID="${FIRESTORE_DATABASE_ID}",_SECRET_PREFIX="${SECRET_PREFIX}",_SERVICE_ACCOUNT="${SERVICE_ACCOUNT}"
```

## Verification

Service checks:

```bash
curl -fsS "${TOOL_URL}/health"
curl -fsS "${TOOL_URL}/.well-known/jwks.json"
curl -fsSI "${TOOL_URL}/js/canvas-seb-detector.js"
curl -fsS "${TOOL_URL}/lti/config"
```

Canvas checks:

1. Install the LTI key from `${TOOL_URL}/lti/config`.
2. Install the app by Client ID at the Canvas account or pilot course.
3. Add the detector script loader to the Canvas theme.
4. Launch the tool from a course as an instructor.
5. Complete Canvas OAuth.
6. Refresh course content.
7. Enable SEB on one Classic Quiz and one New Quiz if available.
8. Download the `.seb` file.
9. Open it in SEB on a client with the matching certificate identity installed.
10. Confirm Config Key proof fills the Canvas access code, completion cannot be triggered by ambient page changes, and the user must explicitly choose the exit-page quit action.

## Updating Secrets

For rotations, add a new Secret Manager version and redeploy:

```bash
printf '%s' "NEW_VALUE" | gcloud secrets versions add "${SECRET_PREFIX}_state_encryption_key" --data-file=-
gcloud builds submit --config=cloudbuild-school.yaml --substitutions=_SERVICE="${SERVICE_NAME}",_IMAGE="${IMAGE_NAME}",_FIRESTORE_DATABASE_ID="${FIRESTORE_DATABASE_ID}",_SECRET_PREFIX="${SECRET_PREFIX}",_SERVICE_ACCOUNT="${SERVICE_ACCOUNT}"
```

Changing `STATE_ENCRYPTION_KEY` invalidates outstanding LTI/OAuth state and sessions that depend on it. Rotate it outside active exams.

Changing `LTI_PRIVATE_KEY` changes the public JWKS. Update Canvas or let Canvas refresh JWKS before active use.

Changing the SEB config-encryption certificate requires deploying the matching private identity to SEB clients before new encrypted configs are downloaded.

Each Cloud Build captures the registry digest returned by its exact build-tag push and deploys Cloud Run with `@sha256:...`; it does not resolve a mutable tag in a later step. Verify the deployed revision digest after every build. Mutable cache tags are never the deployment identity.
