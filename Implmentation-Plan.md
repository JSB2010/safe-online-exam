Implementing a Secure Safe Exam Browser Integration for Canvas Quizzes
Overview of the Challenge
Canvas currently lacks a native Safe Exam Browser (SEB) integration (unlike Moodle or Blackboard), so any enforcement must be done via a custom solution. The previous approach (using Canvas modules and redirect links) could be easily bypassed because the quiz itself wasn’t locked down – students could navigate directly to the quiz URL in a normal browser. We need a more secure workflow so that quizzes marked for SEB can only be accessed through SEB, with proper safeguards to prevent cheating.
Proposed Solution Summary
To securely enforce SEB on Canvas quizzes, the solution is to integrate at the quiz level using Canvas’s own restrictions, combined with providing a Safe Exam Browser configuration file to students. In essence, when an instructor toggles “SEB mode” for a quiz, the system will:
	•	Lock the quiz with an access code (password) known only to the SEB configuration. This ensures that even if students find the quiz link, they cannot start it outside of SEB.
	•	Generate a .seb configuration file for Safe Exam Browser, pre-configured with the quiz URL, required password, and any allowed settings. Students use this file to launch the quiz in SEB.
	•	Detect the browser environment: If a student attempts to open the quiz in a normal browser (without SEB), they either see a friendly message instructing them to use SEB (via an LTI launch page) or simply encounter the password prompt which they cannot bypass. In SEB, the quiz proceeds normally because the config provides the needed credentials/settings.
	•	Allow instructor customization of SEB settings (allowed URLs, quit password, etc.) either through a simple UI or by letting them upload/edit the SEB config, while still enforcing the critical settings (start URL and access code).
	•	Support both Classic Quizzes and New Quizzes by leveraging their access code feature and Canvas APIs.
This approach mirrors how other LMS handle SEB. For example, Moodle’s built-in SEB integration requires distributing a secure configuration file to students, and “students will only be able to attempt the quiz if they are using Safe Exam Browser.”[1] Similarly, third-party LTI tools (like Numbas) enforce SEB by having instructors upload a settings file containing the quiz’s Start URL and a special config key[2]. These measures ensure the exam can only be accessed in the locked-down environment.
Implementation Plan and Details
	•	Enforce Quiz Lockdown via Access Codes: When SEB mode is enabled for a quiz, the system should generate a strong random access code (password) and apply it to the Canvas quiz settings using the Canvas API. Both Classic Quizzes and New Quizzes support a “require access code” option[3][4]. This means no student can begin the quiz without entering the correct code. By itself, a password adds security; in our case, we won’t directly give this code to students at all – it will be delivered through the SEB config. This is analogous to how Respondus LockDown or Moodle ensure only the lockdown browser can open the exam. If a student tries to launch the quiz URL in a regular browser, they’ll be stopped at a password prompt (or an LTI intermediate page) which they cannot get past without SEB.
	•	Generate a Safe Exam Browser Configuration File: Along with setting the quiz password, the LTI app will generate a .seb configuration file tailored to that quiz. The configuration file includes all the rules and settings for SEB. Key elements to configure:
	•	Start URL: This is the Canvas quiz URL (e.g. https://yourcanvas.instance/courses/123/quizzes/456). When opened, SEB will navigate directly to the quiz’s start page[5]. (For New Quizzes, use the appropriate launch URL for the quiz/assignment.)
	•	Configured Password: The quiz access code can be embedded in the SEB settings so that when SEB loads the quiz, it can automatically pass the code (or at least the student is already in the correct environment to receive it). Some SEB configurations allow an auto-login or can include the password as part of the start URL or via script. If automatic entry isn’t possible, the instructor can disclose the password only within the SEB environment (e.g. in the quiz instructions visible in SEB), but not beforehand. This way, a student not using SEB won’t know the code.
	•	Allowed Domains/Resources: By default, the SEB file should restrict browsing to only the Canvas domain (and perhaps any necessary resources like image/CDN domains used by Canvas). The instructor can add specific URLs if the quiz needs to allow certain external sites (using SEB’s URL filter feature)[6][7].
	•	Security Options: Configure SEB to disable navigation features, keyboard shortcuts, screen capture, etc., as needed (many of these are default with SEB[8]). For example, disable secondary browser windows, back/forward navigation, and restrict switching applications – SEB handles these by default when running[1][9].
	•	Quit Password (Optional): The instructor may set a SEB “quit password” in the config if they want to prevent students from exiting SEB during the exam without permission. This can be exposed as a setting in the UI.
	•	Browser Exam Key (Advanced): The SEB config tool can generate a unique Browser Exam Key hash for the exam settings[10]. In a fully secure setup, the server (Canvas or our LTI) would verify this key from the SEB browser’s HTTP headers to ensure the client is using the correct, unmodified config. Canvas doesn’t natively do this, but our LTI app could implement a verification step if we route the launch through it. For the initial implementation, this might be skipped for simplicity, but it’s worth noting as a future enhancement for higher security (to detect if someone spoofed the user-agent string, for example).
	•	Link to Quit after Submission: Optionally include a quit link that SEB can use to automatically close or quit after the quiz is submitted[11]. This could be a URL (perhaps the Canvas course homepage or a specific “end exam” page) that, when loaded, triggers SEB to release control. Moodle, for instance, uses a special quit link so that when the exam is over, students can exit the lockdown easily[12].
The LTI app can programmatically create this .seb file. (SEB config files are essentially XML/JSON with a specific schema and can be generated or modified by code.) In Moodle’s case, admins can either manually configure these settings or upload a pre-made config[13]. In our solution, we’ll automate it to be user-friendly: once the teacher clicks “Enable SEB for this quiz,” the app produces a downloadable configuration file on the spot.
	•	Instructor LTI Interface (Toggle & Settings): The integration will be provided as an LTI tool installed at the course level (only teachers see its interface). Instructors will use this tool to manage SEB settings for quizzes. Key aspects of the UI/UX:
	•	The LTI app can list all quizzes in the course (via Canvas API) with an indicator if SEB mode is enabled. The teacher can toggle a particular quiz “Require Safe Exam Browser” on or off.
	•	When turning it ON: behind the scenes, the app generates the random access code and calls Canvas API to update the quiz with this code (and maybe an informational note in the quiz description like “This quiz requires Safe Exam Browser”). It then generates the SEB config file as described and presents a “Download SEB Config” button to the instructor. The config file name could include the quiz name or ID for clarity.
	•	Optionally, provide a “SEB settings” form for common options. For example, a text field to add allowed web domains, a checkbox to require a quit password (and field to set that password), dropdowns for enabling/disabling certain features (like “allow reload button” etc.). This isn’t strictly necessary for a basic solution, but it greatly improves usability, since the instructor can customize the lockdown level from Canvas directly. (If not provided initially, an alternative is to allow the instructor to download the config, edit it in the SEB Config Tool, then re-upload – but direct options in the LTI are more convenient.)
	•	When turning it OFF: the app should remove the requirement. This would involve possibly removing the access code from the quiz (or clearing it) and perhaps deleting any stored config in the app’s database. Essentially, restore the quiz to normal Canvas behavior. (We must ensure that disabling SEB mode re-opens the quiz properly, perhaps also advising the teacher to inform students they no longer need SEB.)
	•	The LTI app would need appropriate API permissions (via Canvas developer key) to update quiz settings (for both classic and new quizzes). For Classic Quizzes, use the Quiz API to set the access_code. For New Quizzes (which are LTI-based), use the New Quizzes API or Canvas GraphQL to set the “Require student access code” setting. This ensures both quiz types are covered as requested.
	•	Student Workflow: The goal is to make it easy for students to launch the quiz in Safe Exam Browser, and impossible to do so otherwise. Here’s how it would work for them:
	•	The instructor provides students with the SEB config file for the quiz. For example, the teacher might upload it to a Canvas module or quiz instructions (or the LTI app could even create a placeholder module item). Students would download this .seb file to their computer. (In the future, the LTI could also offer a direct “Open in Safe Exam Browser” link that uses the safeexambrowser:// URL protocol to auto-launch SEB, similar to Moodle’s Launch Safe Exam Browser button[14], but providing the file is a simple universal method.)
	•	Before the exam, students must have Safe Exam Browser installed on their device. (The teacher should communicate this and perhaps include the download link. SEB is available for Windows, Mac, iOS, etc. as noted in documentation[15].)
	•	At exam time, the student opens the .seb file, which will automatically launch Safe Exam Browser with the predetermined settings. SEB will open directly to the Canvas quiz’s start page (the login screen or quiz introduction). Because of our settings:
	•	If the Canvas session isn’t logged in yet, the student might need to log in to Canvas within SEB (so ensure they know their Canvas credentials). Once logged in, they navigate to the quiz (the Start URL should redirect them correctly after login).
	•	When the quiz page loads, Canvas will prompt for the quiz access code. Now, since the student is in SEB, it’s safe to provide the code. If we configured the SEB file to auto-enter the code (via a script or specialized SEB setting), it would happen here. Otherwise, the teacher can give the code verbally or on a physical board at exam start (for proctored in-class exams), or include it in the quiz instructions (which are now visible only in SEB, so a student who isn’t in SEB can’t see them). For example, the quiz instruction could say “Access Code: XXXXXX (only open in Safe Exam Browser)”. Because a student in a normal browser can’t get past the code gate, they won’t see these instructions.
	•	The student enters the code (if not auto-filled), and begins the quiz. From here, SEB locks down their environment — no switching apps, no screen capture, only Canvas pages allowed, etc. The quiz proceeds as normal inside SEB, with all Canvas functionalities intact. They answer questions and submit as usual.
	•	Upon submission, if configured, SEB can present an exit button that uses the quit link to close the browser[12]. If not, the student can exit SEB by using the quit password or by an allowed method after finishing.
	•	What if a student tries to cheat? If they attempt to open the quiz in a regular browser without SEB, they will hit a roadblock. One scenario is that they click on the quiz in Canvas and see a page asking for the access code. Since they don’t know it (it was never shared openly), they cannot proceed. Alternatively, we could improve this UX: the LTI app could create a placeholder launch page (via an external tool URL) that the quiz link directs to when SEB is required. This page would detect the user-agent or a custom HTTP header that SEB sends.
	•	If the student is not in SEB (i.e., normal browser), it would display a clear message: “This quiz can only be taken using Safe Exam Browser. Please download the configuration file and open it to start the exam.” and perhaps provide the .seb file download there too.
	•	If the student is in SEB (the user-agent string for SEB contains identifiers, or SEB can include a special header like X-SafeExamBrowser), the page could immediately redirect them to the actual quiz URL and possibly auto-submit the access code. This creates a seamless experience: SEB users go straight in, others get instructions.
	•	However, even without this fancy redirect page, the access code alone provides security. The message page is just a nicer touch. The crucial part is that no code = no entry for unauthorized browsers. Students would realize they must use the provided SEB file.
	•	Instructor Customization of SEB Settings: Since SEB offers a wide range of security and convenience settings[13], the solution should be flexible:
	•	At minimum, have sensible default settings in the generated config (e.g., no external web access except Canvas, disable all hotkeys, no browser UI). This covers most use cases out of the box.
	•	Provide an option for instructors to allow certain sites or resources if their quiz needs it (for example, an embedded video from YouTube or a link to an e-book). This could be a simple comma-separated list of URLs or domains in the LTI interface, which the app then inserts into the SEB config’s allowed URL list. SEB supports URL filters where you can whitelist specific domains or patterns[6][7].
	•	For more advanced control, the LTI could have a mode where the instructor uploads a custom .seb file (for those comfortable using the official SEB Config Tool). For instance, an instructor might craft a config with very specific settings using the SEB tool, then upload it. The app would then only tweak the critical fields (like Start URL, the exam password, Browser Exam Key) to match the current quiz and ensure consistency. This gives power users full control while still tying the config to the Canvas quiz.
	•	Any instructor-provided settings (via UI or uploaded file) should be stored in the LTI app’s database and reapplied whenever the config is downloaded or if the quiz is re-enabled. This way, if they toggle off/on or revisit, their customizations persist.
	•	Compatibility with Classic and New Quizzes: The solution should handle both Canvas quiz types:
	•	Classic Quizzes: Use the Canvas REST API to set the access_code for the quiz (and perhaps the IP filter if needed, though IP isn’t as relevant here). Classic quiz launching is straightforward – the Start URL is the quiz link itself.
	•	New Quizzes: New Quizzes are an LTI tool within Canvas, but they still have a similar concept of an access code[3]. The LTI app may need to use Canvas’s GraphQL API (or any provided endpoint) to set this “student access code” on the New Quiz. The Start URL might be the assignment’s launch URL (Canvas typically shows a “Launch External Tool” button for New Quizzes). We might need to adjust the flow slightly: potentially the SEB Start URL could be the Canvas assignment page that then launches the New Quiz LTI. As long as the access code is set, the student will be prompted for it upon launching the new quiz, which again SEB will handle. Testing and adjusting for New Quizzes will be important, but conceptually it’s the same (lock with code, deliver code via SEB).
	•	The LTI interface can abstract this difference so the instructor just clicks “Enable SEB” regardless of quiz type. Under the hood, the app checks quiz metadata to see if it’s a New Quiz (usually indicated by quiz_lti or similar) and uses the appropriate API calls. From the teacher’s perspective it works uniformly.
	•	Security Considerations: This combined approach (Canvas access codes + SEB config) provides defense in depth:
	•	The Canvas quiz password is a server-side check that ensures no one can access the quiz without the secret. By only embedding that secret in a controlled SEB file (or revealing it under proctored conditions), we close the earlier loophole. Even if a student figures out the quiz URL or tries to use developer tools, the Canvas platform itself demands the code. This is a significant improvement over a simple redirect-based gate.
	•	The SEB environment itself provides the actual device lockdown: once the student is in SEB with our config, they cannot switch apps, visit unauthorized sites, or take screenshots[8]. This dramatically reduces cheating opportunities compared to a normal browser.
	•	Using a config file also means we can leverage SEB’s built-in verification features. While Canvas doesn’t natively validate a Browser Exam Key, our integration could be extended to do so. For example, we could include a known Config Key in the SEB settings (essentially a hash of the permitted config) and have our LTI tool verify it by inspecting a header or a script during quiz launch[10]. If the environment is wrong, the LTI could refuse entry. This is similar to how Moodle uses a “Config Key” header to ensure the SEB client is properly configured[16]. Implementing this would be an advanced step (possibly involving a small JS snippet in the quiz page or a custom proxy), but it’s good to know it’s possible.
	•	We should also secure the LTI app itself. Only teachers (and admins) should have access to the interface that toggles SEB mode and retrieves the config file. Students should not be able to misuse the LTI to get the password. Using Canvas’s role differentiation in LTI (or checking ext_roles in LTI launch) will ensure only teachers see the controls. When a student launches the LTI (if they somehow find it), it should either do nothing or simply show a message about how to get the .seb file.
	•	The generated access codes should be sufficiently complex and unique per quiz to prevent guessing. If the code or the SEB file is leaked, the instructor can always regenerate (toggle off/on to produce a new code and file). It might be wise to regenerate the code for each course offering or each semester.
	•	Finally, instruct instructors to keep the .seb file secure until needed (don’t post it too early or where unauthorized people can get it). Possibly, the file could be made available just before the exam (Canvas has the ability to set availability dates on files or modules).
Implementation Steps Recap
In summary, the plan to achieve a robust SEB integration for Canvas is:
	•	Develop the LTI management app (preferably LTI 1.3 for modern Canvas) that allows instructors to enable “Require Safe Exam Browser” on specific quizzes.
	•	Use Canvas APIs to apply a quiz access code and store it when SEB mode is enabled.
	•	Dynamically generate a Safe Exam Browser settings file containing the quiz URL, lockdown settings, and embed the access code (directly or indirectly) for student use. Provide this file to instructors for distribution.
	•	Incorporate user-agent or header checks in the launch flow (via the LTI or a lightweight redirect page) to gracefully handle students not in SEB (show download instructions) vs. in SEB (allow entry).
	•	Allow configuration options for instructors (at least for whitelisting URLs and setting a quit password, with potential to extend to full config uploads or templates later).
	•	Test on both classic and new quiz types to ensure the workflow is smooth (especially the part where SEB passes the access code – adjustments may be needed to ensure the student isn’t stuck at the password prompt).
	•	Iterate for security: add enhancements like verifying the SEB client’s config (exam keys), and keep user experience simple (one-click for teachers to set up, one file for students to open).
By implementing the above, we effectively replicate what first-party integrations do: students can only open the quiz through the secure SEB environment[1], and any attempt to bypass will fail. The combination of Canvas’s own restrictions and SEB’s lockdown creates a secure and user-friendly solution for Canvas quizzes with minimal hassle for instructors and students alike.
Sources: The design takes cues from how Moodle and other platforms integrate SEB, requiring a config file and locking down quiz access[17][2], as well as Safe Exam Browser’s official guidelines on using access keys and config passwords[18][10]. These practices inform a solution that is both secure and easy to use for our Canvas environment. The end result will give instructors a much-needed toggle for secure exams, and give students a clear, simple path to take those exams with Safe Exam Browser.
